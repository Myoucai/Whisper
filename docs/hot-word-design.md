# 词级热编译（分发架构第 4 级）——设计备忘与立项决策

状态：**立项不动工**（2026-09-04 决策）。本文记录机制设计、前置条件与
重启触发器，避免未来重新论证。

## 机制（若启动）

```
profiler（词调用计数，环形采样）
  → 阈值命中的热词：word_dict["name"] 的 Rc<[Opcode]>
  → 复用现有 Rust transpiler 生成单词 C 片段（W_<name> 函数）
  → 后台调宿主 cc -O2 -march=native -shared 编译为 .so/.dll
  → dlopen + dlsym 拿函数指针
  → word_dict 原子换绑：Opcode 序列 → CallNative(fn_ptr) 单指令桩
```

关键点：全部代码生成复用 `-t c` 既有路径（W_qN 引号函数、w_op_* 分派
helper 已与 VM 语义逐位对齐——这是本轮 tag 化统一的直接收益），
不写新后端。

## 前置条件（启动前必须满足）

1. **实测 VM 计算瓶颈**：存在真实负载其执行时间的多数在 VM dispatch
   而非 I/O。当前测量：Lexicon 全链路瓶颈在 HTTP 延迟；`-t c2` 首建
   ~27s 主要是 VM 跑编译器，但 `-t native` 的内容寻址缓存已把重复
   构建降为 16ms——首次构建的加速收益边际。
2. **逐词等价证明**：编译片段与解释执行在 B2 栈合同 + 语义对拍上
   逐位等价（可复用 c_backend_tests 的对拍基建，按词粒度跑）。
3. **换绑协议**：单写者（编译线程）+ 读者（VM 线程）经不可变
   `Rc<[Opcode]>` 原子换绑；dlopen 句柄生命周期与 VM 进程一致
   （不做卸载，避免撕扯）。
4. **缓存与失效**：词源哈希 + 编译器版本 + march 键（复用
   `-t native` 的指纹函数），落同一缓存目录。

## 风险清单

- tiering 的经典复杂度：解释/编译双路径语义漂移、热换绑时刻的栈
  一致性、调试困难（V8/.NET 在此花费数百人年）；
- Windows dlopen（LoadLibrary）与代码签名/杀软交互；
- 收益不确定：见前置条件 1——当前无计算瓶颈负载。

## 重启触发器

出现以下任一情形时重新评估：

- 某真实工作负载剖析显示 VM dispatch 占执行时间 >50%；
- `-t c2` 首建时间成为可用性障碍（且无法用缓存解决）；
- 嵌入式/边缘部署要求持续运行的自改进性能（Lexicon 词库分发后
  在低配设备上的持续加速）。

## 已交付的替代路径

分发架构第 2/3 级已落地并覆盖热编译的大部分收益场景：

- `-t native`：安装期 `-O3 -march=native -flto` + 内容寻址缓存
  （重复构建 16ms）；
- `-t exe`：自包含单文件分发；
- C 后端与 VM 算术逐位一致（tag 化 wval），保证未来热编译片段的
  等价性可证。
