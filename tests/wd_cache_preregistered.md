# 收口 ③：`wd` 的内容寻址缓存（预注册）

2026-09-21 立项。仿前几份：**判据先写死，再动代码**。

## 目标与理由

`wd run` 现在每次都重跑一遍 gcc。设计文档（`docs/independence-design.md`
Step 3 节）早就写了要做内容寻址缓存，一直没做。

## 设计决定（提前写明）

**缓存的是 gcc 的产物，缓存键 = hash(生成的 C 文本 ++ `runtime.c` 内容 ++ cc 名)。**

- **为什么不把"编译器版本"放进键**：同一份 C 经同一个 cc 出来就是同一个二进制，
  所以不需要记住"是谁生成的"。把编译器身份放进键反而会引入一条**脆弱不变式**
  ——改了 `wd` 却忘了 bump 版本号，缓存就会一直吐旧产物。
  把 **生成的 C** 当键的原料，这条不变式就自动成立。
- **为什么键里必须有 `runtime.c`**：它以 `#include "runtime.c"` 的形式被引用，
  **不在 C 文本里**。只哈希 C 文本的话，改了运行时不会失效。
- **哈希函数**：多项式 64 位（`h = h*1099511628211 + byte`，i64 自然回绕），
  结果拼上**原文长度**。不做加密强度——这是本机 `target/` 下的构建缓存，
  输入非对抗。长度入键是为了让"内容不同但哈希撞车"在长度上先分道。
- **缓存位置**：`<WHISPER_ROOT>/target/whisper-cache/<key>`。
- **只缓存 `wd run` 的产物**（`wd build` 的输出路径由调用者指定，命中也要复制
  一次，收益相同；两者共用同一段代码，不特判）。

## 判据

- **C-1（正确性，最重要）** 对同一程序：第一次 `wd run` 与第二次 `wd run`
  的**输出逐字节相同**，且都与"从零编译并直接运行产物"相同。
- **C-2（真的命中了）** 第二次调用**不再生成 `W_*` 函数**——判据是第二次
  比第一次快，且缓存目录里出现了对应条目。**用可观测的事实，不用感觉**：
  在缓存目录里的文件数从 0 变 1，且第二次的 wall time 明显更短。
- **C-3（改输入必失效）** 改**源码** → 新条目（旧条目仍在），输出随之改变。
- **C-4（改运行时必失效）** 改 `runtime.c`（判据用临时追加一个注释再还原，
  或用 `WHISPER_ROOT` 指向一份改过的副本）→ **不得命中旧条目**。
- **C-5（零回归）** 既有 wd 冒烟四条、`w2_wd_output_matches_c2_byte_for_byte`、
  `wd_driver_compiles_and_runs_when_present` 全过；六闸与固定点不回归。
- **C-6（失败不进缓存）** gcc 失败时**不得**写入缓存条目——否则一次偶发失败
  会被永久记住。

## 反向判据（什么算失败，提前写明）

- 为了省事把缓存键设成"源码文件路径 + mtime" → **失败**：改内容不改 mtime
  的工具链会命中错产物，而且 `wd` 是零 Rust 驱动，不该依赖时间戳。
- 失败时也写缓存 → **失败**（C-6）。
- 命中后不产出调用者要的 `<out>` → **失败**：那是偷偷改契约。
  `wd run <src> <out>` 仍必须留下 `<out>`。

## 执行记录（2026-09-21，第 5 轮：大字面量被排除，转 S-4）

**结果**：仍然回退。但**排除了上一轮留下的唯一嫌疑**，并且把范围又缩窄了一格。

### 决定性实验

把两个只差乘数的词放在**同一次编辑、同一次构建**里（吸取上轮"调试动词引用了
被回退掉的词、脚本静默用旧二进制"的教训），一次运行同时算：

```
: wd-hash-s { dup strlen swap strchars 0 { swap 1000003   * swap + } @fold swap i64tostr "-" strcat strcat } ;
: wd-hash-L { dup strlen swap strchars 0 { swap 1099511628211 * swap + } @fold swap i64tostr "-" strcat strcat } ;
```
输出：`S=` 之后立刻 `type error: expected ptr` —— **小乘数也挂**。

**所以 `1099511628211` 无罪。** 上一轮"嫌疑转向大字面量"的判断被推翻。

### 现在还剩什么可疑（给下一轮）

把 `wd-hash-s` 与上一轮**验通过的**那段并排看，差别只有两处：

| 上一轮验通过（在 `wd-hashdbg` 里） | `wd-hash-s` 里 |
|---|---|
| `dup` 然后 `strchars …` | `dup strlen swap` 然后 `strchars …` |
| 折叠结果直接 `.` 打印 | `swap i64tostr "-" strcat strcat` |

**下一轮第一步（很便宜）**：把这两处分别试。
1. 先只加尾部：`dup strchars 0 { swap 1000003 * swap + } @fold swap i64tostr "-" strcat strcat .`
2. 再只改前缀：`dup strlen swap strchars drop .`
哪一步炸，就是哪一步。

### 转 S-4

③ 已连续三轮只产出"缩小失败点"。**按第 4 轮说好的，本轮之后转去做 S-4**
（`std/str` 与 `std/list` 的 `nth` 同名冲突）与词表对拍——那两项形状已知、
判据可机械验证，比继续在这里磨更划算。③ 的进度都留在本文件里，随时可接。

### 反向判据自查

三项仍然通过：键是内容哈希不是 mtime；失败不写缓存；没有改 `wd run` 的契约
（回退后冒烟四条 + 多行限定名两条全过）。


**结果**：仍然没有可用的缓存，仍然整文件回退。但**把失败点从"十一行的词"缩到了
一行表达式**。

### 二分结果（按上一轮写的路线做的）

用临时调试动词把 `wd-hash` 拆成逐步打印，一次构建全跑完：

```
dup strchars len .                                     → A 3      ✅ strchars 通
dup strchars 0 { + } @fold .                           → B 294    ✅ 折叠通道通
dup strchars 0 { swap + } @fold .                      → C 294    ✅ 带 swap 的体
dup strchars 0 { swap 1 * swap + } @fold .             → D 294    ✅ 带乘法（乘数 1）
dup strlen .                                           → E 3      ✅
```
（288 = 97+98+99 ✓，说明每一步的算术都对。）

**唯一没验过的是真实乘数 `1099511628211`。** 而上一轮 `wd-hash` 整体报
`expected ptr` 时，那十一行里与上面唯一的差别就是它。

### 两条给下一轮的硬信息

1. **`wd-hash` 的折叠体形状是对的** —— `strchars 0 { swap P * swap + } @fold`
   这条通道本身在自举链上通（用 P=1 验过）。所以不必再怀疑"`@fold` 引号体的
   栈形状与预期不同"这条上轮写下的怀疑点，**它不是原因**。
2. **重点转向那个大乘数**。生成的 C 里它是 `W_I64((int64_t)1099511628211L))`，
   **字面量发射本身是对的**，所以嫌疑落在"`fuse-hof` 把这个引号体抬成顶层
   静态函数之后，体里的大字面量"这条路上。
   **下一轮第一步**：把乘数换成 `1000003`（小到能进 32 位）再跑一次 `wd hash`。
   若通过 → 就是大字面量；若仍失败 → 换 `h*2+1` 之类完全不依赖大常数的混合。

### 本轮踩的坑（记下来免得重犯）

`git checkout` 回退 `wd.ws` 之后再往上加调试动词时，我调用了**已被回退掉**的
`wd-hash`，于是构建失败、而测试脚本静默用了**上一次的旧二进制**，打出一批看似
正常的 A–E —— 白读了一轮。**教训：临时调试动词必须与被验的词同一次编辑加入、
同一次构建验证；看到输出先确认二进制是新的。**

### 反向判据自查

三项仍然通过：键是内容哈希不是 mtime；失败不写缓存；没有改 `wd run` 的契约
（回退后冒烟四条 + 多行限定名两条全过）。


**结果：仍然验证不通过，仍然整文件回退**（回退后冒烟四条 + 多行限定名两条全过）。

### 这一轮做的（按上一轮自己写的路线：先单独验 `wd-hash`）

加了 `wd-hash` 与一个临时调试动词 `wd hash <s> pad`（`wd-argv` 要求 4 个参数
才放行，所以要有占位参数），把哈希从缓存接线里**摘出来单独喂输入**。
这一步是有价值的——两轮都在"整条链路"上看同一个报错，什么也看不出来。

**进程**：

| 轮次 | 现象 | 结论 |
|------|------|------|
| 上一轮 | 整链路 `expected ptr`，缓存目录为空 | 定位不到 |
| 本轮 第 1 次 | 调试动词报 `stack underflow` | **是调试动词自己的 bug**：`wd-main` 的 true 分支先 `drop` 了 argv，`wd-hashdbg` 又去 `1 @nth` |
| 本轮 第 2 次 | 改成 `dup 1 @nth wd-hash . drop` 后 → `expected ptr` | **错确实在 `wd-hash` 内部** |

即：失败点从"整条链路"缩小到了**一个十一行的词**。这是这轮唯一的实质进展。

### `wd-hash` 的形状（下一轮从这个表达式直接二分）

```
: wd-hash {
    dup strlen                     // s len
    swap                           // len s
    strchars 0 { swap 1099511628211 * swap + } @fold   // len h
    swap i64tostr "-" strcat strcat                    // "h-len"
} ;
```

下一轮**从最小处试起**，不要再整条跑：

1. `strchars 0 { + } @fold .` —— 先确认"字节列表 + 初值 0 + 折叠"这条通道本身通。
2. `strchars 0 { swap 1099511628211 * swap + } @fold .` —— 换成真正的折叠体。
3. `dup strlen swap strchars drop .` —— 确认 `dup strlen swap` 这段没把栈弄乱
   （`strchars` 在自举前端解析出的到底是不是 opcode 184）。
4. 最后才拼 `i64tostr "-" strcat strcat`。

怀疑点（未证实，供参考）：`@fold` 的引号体在自举链的 `fuse-hof` 路径上拿到的
栈形状；以及 `1099511628211` 这个字面量在自举前端的取值。

### 反向判据自查

三项仍然通过：键是内容哈希不是 mtime；失败不写缓存；没有改 `wd run` 的契约
（回退后行为与提交版逐字节一致，冒烟全过）。
