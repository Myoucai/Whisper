# 收口 ③：`wd` 的内容寻址缓存（预注册）

2026-09-21 立项。仿前几份：**判据先写死，再动代码**。

## 目标与理由

`wd run` 现在每次都重跑一遍 gcc。设计文档（`docs/independence-design.md`
Step 3 节）早就写了要做内容寻址缓存，一直没做。

## 设计决定（提前写明）

**缓存的是 gcc 的产物，缓存键 = hash(生成的 C 文本 ++ `runtime.c` 内容 ++ cc 名)。**

- **为什么不把"编译器版本"放进键**：同一份 C 经同一个 cc 出来就是同一个二进制，
  所以不需要记住"是谁生成的"。把编译器身份放进键反而会引入一条**脆弱不变式**
  ——改了 `wd` 却忘了 bump 版本号，缓存就会一直吐旧产物。
  把 **生成的 C** 当键的原料，这条不变式就自动成立。
- **为什么键里必须有 `runtime.c`**：它以 `#include "runtime.c"` 的形式被引用，
  **不在 C 文本里**。只哈希 C 文本的话，改了运行时不会失效。
- **哈希函数**：多项式 64 位（`h = h*1099511628211 + byte`，i64 自然回绕），
  结果拼上**原文长度**。不做加密强度——这是本机 `target/` 下的构建缓存，
  输入非对抗。长度入键是为了让"内容不同但哈希撞车"在长度上先分道。
- **缓存位置**：`<WHISPER_ROOT>/target/whisper-cache/<key>`。
- **只缓存 `wd run` 的产物**（`wd build` 的输出路径由调用者指定，命中也要复制
  一次，收益相同；两者共用同一段代码，不特判）。

## 判据

- **C-1（正确性，最重要）** 对同一程序：第一次 `wd run` 与第二次 `wd run`
  的**输出逐字节相同**，且都与"从零编译并直接运行产物"相同。
- **C-2（真的命中了）** 第二次调用**不再生成 `W_*` 函数**——判据是第二次
  比第一次快，且缓存目录里出现了对应条目。**用可观测的事实，不用感觉**：
  在缓存目录里的文件数从 0 变 1，且第二次的 wall time 明显更短。
- **C-3（改输入必失效）** 改**源码** → 新条目（旧条目仍在），输出随之改变。
- **C-4（改运行时必失效）** 改 `runtime.c`（判据用临时追加一个注释再还原，
  或用 `WHISPER_ROOT` 指向一份改过的副本）→ **不得命中旧条目**。
- **C-5（零回归）** 既有 wd 冒烟四条、`w2_wd_output_matches_c2_byte_for_byte`、
  `wd_driver_compiles_and_runs_when_present` 全过；六闸与固定点不回归。
- **C-6（失败不进缓存）** gcc 失败时**不得**写入缓存条目——否则一次偶发失败
  会被永久记住。

## 反向判据（什么算失败，提前写明）

- 为了省事把缓存键设成"源码文件路径 + mtime" → **失败**：改内容不改 mtime
  的工具链会命中错产物，而且 `wd` 是零 Rust 驱动，不该依赖时间戳。
- 失败时也写缓存 → **失败**（C-6）。
- 命中后不产出调用者要的 `<out>` → **失败**：那是偷偷改契约。
  `wd run <src> <out>` 仍必须留下 `<out>`。

## 执行记录（2026-09-21，第 9 轮：**抓到并修掉一个真 bug；存储仍未落盘**）

**结果**：仍回退，但这一轮有实质收获——**`wd-real` 的一个潜在 bug 被定位并验证修复**。

### 定位方法（第 11 轮证明有效的那套，这次用对了）

在 `wd-build` 的缓存块里插 `|1`..`|8` 打印，**一次构建**就看出了挂点：

```
|1 |2 |3 119431 |4 119434 |5 -5589980590998521177-119434
|6（同）|7 D:/Whisper/target/whisper-cache/-5589980590998521177-119434 |8
→ type error: expected ptr
```
前七步全对，挂在 `|8`（`wd-real`）。

### 真凶：`wd-real` 返回**两个**值

```whisper
: wd-real {                        // 原写法
    dup file-exists ?? return ]            // 这条路径 ✓ 返回一个
    dup ".exe" strcat                      // [原名, 原名.exe]
    dup file-exists ?? return ]            // ✗ 返回两个
    drop ""                                // ✗ [原名, ""] 也是两个
} ;
```
旧调用处只按**栈顶**判断（`dup strlen 0 =`），不按深度取槽，所以这个泄漏一直没暴露；
一旦调用方用 `dup 2 @nth` 取自己的槽，多出来的一个值就让它取错对象 —— 正是
`expected ptr`。

**修法**（已验证）：
```
    dup file-exists ?? swap drop return ]   // 丢掉原名，只留 +.exe
    drop drop ""                            // 两个都丢掉
```

**实测**：插着打印跑，八步全过、`exit=0`、输出 `wd: compiled -> … 3`。修完去掉打印
再跑，运行正常。**这一处修复本身是干净且有价值的**（`wd-real` 是既有代码），
下一轮应当**单独把它提交**，不要再和缓存捆在一起。

### 仍未解决：缓存条目始终为 0

`wd-cp` **无条件返回 0**（`@10 drop 0`），拷贝失败完全不可见 —— 下一轮第一件事
就是让它返回 `@10` 的真实 status，否则这个问题无法诊断。

下一轮要么只比**转发段**（`tail -n +2`），要么把路径归一化。

### 事实

- 挂点在**键计算段**（`wd-build` 里 gcc 之前的六步）：

  我对每一步都手工走过栈，形态是对的；但**其中至少一步在真实上下文里不对**。

### 下一轮：不要再手工走栈（这是第五次了）

前四轮 + 本轮，我每次都"手工走栈认为对"，然后失败。第 11 轮证明了唯一有效的
做法：**在被测代码内部逐行打印、一次构建**。下一轮就照做，**在 `wd-build` 的
缓存块里插打印**：

```
dup 2 @nth ".c" strcat read-file "|1" .        // 读回 .c
wd-root "/whisperc/runtime.c" strcat read-file "|2" .   // 读 runtime.c
strcat "|3" . dup strlen .                     // 拼接 + 长度
wd-cc strcat "|4" . dup strlen .               // 加 cc 名 + 长度
wd-hash "|5" . dup .                           // 算键
"wd.key" swap kv-set "wd.key" kv-get "|6" . dup .   // KV 往返
wd-cache-path "|7" . dup .                     // 路径
wd-real "|8" . dup .                           // 命中探测
```
每插一处构建一次（约 40 秒），或者一次全插、看打印停在哪一步。**一次全插更快**，
打印的顺序会直接指出挂点。

### 已验证可用的表达式（下一轮直接抄）

```whisper
: wd-hash {                        // [s] → "哈希-长度"
    dup strlen swap                                   // len s
    dup strchars 0 { swap 1000003 * swap + } @fold    // len s h
    swap drop                                         // len h
    i64tostr swap i64tostr "-" swap strcat strcat     // "h-len"
} ;
```

实测（`wd hash abc pad`，调试动词 `{ 1 @nth wd-hash drop }`）：

```
|h= 97000680001266 97000680001266-3
   ↑ 折叠结果        ↑ 最终键（哈希 + "-" + 长度 3）
exit=0，stderr 为空
```

**关键就是尾部**：`i64tostr swap i64tostr "-" swap strcat strcat`。
上一版用的 `swap i64tostr "-" strcat strcat` 在 `[len,h]` 上会拼成 `hlen-`，
格式是错的——那是我前面几轮真正抓到的唯一一处**代码** bug。

前四轮 `<3/14>` 的失败**很可能全部出在我的探针上，而不是 `wd-hash`**：

### 本轮拿到的硬事实

1. **折叠 + 乘法完全可用**：`dup strlen swap strchars 0 { swap 1000003 * swap + } @fold`
   实测输出 `97000680001266`（对 `"abc"` 的三个字节算出的大整数，形态正确）。
   第 5 轮怀疑的"折叠通道"到此**两轮连续被证明无罪**（第 4 轮用乘数 1、本轮用
   1000003）。
2. **`wd-hash` 本体仍然挂**，这次是 `stack underflow`（第 5 轮是 `expected ptr`，
   因为我改了调用方式）。即问题在 `wd-hash` 自己的序列里，与折叠无关。
3. **静态检查抓到一个真 bug（尚未在运行中体现）**：尾部拼装顺序反了。
   原写法：
   ```
   ... @fold swap i64tostr "-" strcat strcat
   ```
   在 `[len, h]` 上：`swap`→`[h,len]`、`i64tostr`→`[h,"len"]`、`"-"`→`[h,"len","-"]`、
   `strcat`→`"len-"`、再 `strcat`→**`"hlen-"`** —— 键的格式是错的（应为 `"h-len"`）。
   正确写法：
   ```
   ... @fold i64tostr swap i64tostr "-" swap strcat strcat
   ```
   `[len,h]`→`[len,"h"]`→`["h",len]`→`["h","len"]`→`["h","len","-"]`→`["h","-","len"]`
   →`strcat`→`["h","-len"]`→`strcat`→`["h-len"]` ✓
   **这就是本轮该修进 `wd-hash` 的第一处。**

### 下一轮（第 7 轮）的路线：不要再在 `wd-hash` 外面套探针

已经连续三轮栽在"探针自己的栈算错"上（本轮两种错法：把 i64 当字符串、
误以为上一步留下了 `s`）。**下一轮改成在 `wd-hash` 内部逐行加打印**，
每加一行就构建一次，而不是在外面写一个"以为等价"的复现。

具体三步：
1. 换上上面那个正确的尾部，跑 `wd hash abc pad`。若通过 → 收工，开始接缓存。
2. 若仍 `stack underflow` → 在 `@fold` 之后立刻 `dup .` 打印，确认 fold 真的把
   值交出来了（在 `wd-hash` 内部，不是在外面）。
3. 再仍不行 → 把 `strchars` 换成 `drop 0`（即不折叠，直接给常数），确认尾部
   单独可用。

### 决定性实验

把两个只差乘数的词放在**同一次编辑、同一次构建**里（吸取上轮"调试动词引用了

```
: wd-hash-s { dup strlen swap strchars 0 { swap 1000003   * swap + } @fold swap i64tostr "-" strcat strcat } ;
```

输出：`S=` 之后立刻 `type error: expected ptr` —— **小乘数也挂**。

**所以 `1099511628211` 无罪。** 上一轮"嫌疑转向大字面量"的判断被推翻。

### 二分结果（按上一轮写的路线做的）

用临时调试动词把 `wd-hash` 拆成逐步打印，一次构建全跑完：

```
dup strchars len .                                     → A 3      ✅ strchars 通
dup strchars 0 { + } @fold .                           → B 294    ✅ 折叠通道通
dup strchars 0 { swap + } @fold .                      → C 294    ✅ 带 swap 的体
dup strchars 0 { swap 1 * swap + } @fold .             → D 294    ✅ 带乘法（乘数 1）
dup strlen .                                           → E 3      ✅
```
（288 = 97+98+99 ✓，说明每一步的算术都对。）

**唯一没验过的是真实乘数 `1099511628211`。** 而上一轮 `wd-hash` 整体报
`expected ptr` 时，那十一行里与上面唯一的差别就是它。

### 两条给下一轮的硬信息

1. **`wd-hash` 的折叠体形状是对的** —— `strchars 0 { swap P * swap + } @fold`
   这条通道本身在自举链上通（用 P=1 验过）。所以不必再怀疑"`@fold` 引号体的
   栈形状与预期不同"这条上轮写下的怀疑点，**它不是原因**。
2. **重点转向那个大乘数**。生成的 C 里它是 `W_I64((int64_t)1099511628211L))`，
   **字面量发射本身是对的**，所以嫌疑落在"`fuse-hof` 把这个引号体抬成顶层
   静态函数之后，体里的大字面量"这条路上。
   **下一轮第一步**：把乘数换成 `1000003`（小到能进 32 位）再跑一次 `wd hash`。
   若通过 → 就是大字面量；若仍失败 → 换 `h*2+1` 之类完全不依赖大常数的混合。

### 这一轮做的（按上一轮自己写的路线：先单独验 `wd-hash`）

加了 `wd-hash` 与一个临时调试动词 `wd hash <s> pad`（`wd-argv` 要求 4 个参数
才放行，所以要有占位参数），把哈希从缓存接线里**摘出来单独喂输入**。
这一步是有价值的——两轮都在"整条链路"上看同一个报错，什么也看不出来。

**进程**：

| 轮次 | 现象 | 结论 |
|------|------|------|
| 上一轮 | 整链路 `expected ptr`，缓存目录为空 | 定位不到 |
